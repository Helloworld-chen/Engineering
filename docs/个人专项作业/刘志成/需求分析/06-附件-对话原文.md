## T-Z02　AI（需求工程师）

整体判断：主干覆盖到了，但每条的验收边界都偏软。「状态」是散的——审核态、上架态、交易态混成一个词，Z01、Z03、Z04、Z08 各说一套；Z02 的「稳定顺序」没给排序键；Z06 只有通过／驳回，缺「审核中」；Z05 只是约束不是需求；Z09 把权限和留痕揉成一条，也没定义「管理员」从哪来。照这版写不出可执行的验收用例。

| 未定之处／冲突 | 可能造成的影响 |
| --- | --- |
| 状态维度混用：Z01「审核通过且在售」、Z04「驳回／下架／售出」、Z08「违规下架」，未说明是三套独立字段还是单一 status | 四人对同一商品的可见性判断不一致、接口字段对不上；M04 受控写入与 M06 处置谁优先无仲裁 |
| Z04 只说「状态不能乱跳」，无转移表：售出是否自动下架、下架能否重上、举报处理中算不算可售，全未定 | 状态机各写各的，Z01 过滤与 Z03 判定互相打架，测试用例无从下手 |
| Z03 只要求「说清原因」，未定义判定输入与原因枚举 | M02 拿不到确定返回值；2 分钟付款期内第二人下单如何提示无法验收 |
| Z08「违规下架、已有订单不能动」未区分订单阶段（已付款未发货、已送达待确认收货），下架后买家还能否确认 | 与 M02 结算、M07 售后直接冲突；断网演示时谁都说不出预期 |

三个未说清的场景：

1. 同一商品被两人几乎同时下单、买家正处在 2 分钟付款期，第二个人的详情页该显示什么？超时释放后商品是否自动回到在售，要不要通知刚才看到它的人？
2. 卖家被驳回后「改完再提」，是覆盖原记录还是产生新版本？重提待审期间旧版本还展示吗？历史驳回理由给不给卖家看？
3. 一件已付款、已发货、10 秒后自动送达而买家尚未确认收货的商品被举报并核实违规：M06 该不该下架？下架是否阻断 M02 的确认收货与结算？

## T-Z03　学生

1. 第二个买家的详情页显示「已被其他买家锁定，剩余 XX 秒」，不返回 404。超时释放后商品自动回到在售。通知不做——通知不归我，我只在处置或状态变化时写一条事件，由负责 M08 的同学消费。
2. 改完重提产生新版本，旧版本作为历史保留，不覆盖。重提待审期间不公开展示。历史驳回理由对卖家本人可见（在我的商品页里），不对外公开。
3. 已成交的商品不下架：M06 只改商品的审核与出售状态，不动订单；订单继续履约，退款与争议走 M07。所以「举报核实违规时商品已售出」这种情况，商品状态标记为已下架，但订单不受影响。

另外追问一个：商品下架后，买家之前收藏的详情页链接直接打开，会不会 404？

## T-Z04　AI（需求工程师）

**1 有漏洞，在「锁」**：锁应是订单租约，不是商品 status 的枚举值，否则和 Z04 状态机打架。还要定：下单即锁还是付款才锁；超时／取消／付款失败如何释放；释放瞬间两人同抢谁赢；倒计时以 M08 时钟为准还是前端自算；锁定期间商品是否仍在列表（我认为应在，只不可下单）。差一项，「剩余 XX 秒」就是假的。

**2 认可**。补三点：审核与举报记录必须绑 versionId；举报针对 v1 而卖家已提 v2，处置 v1 要不要连带 v2；已售出应冻结不可再改。图片随版本快照还是引用，不写清历史详情会缺图。

**3 有矛盾**：既说「已成交不下架」，又说「已售出标记为已下架」。取后者可行，但要拆字段——listing_status 只管可售性，与订单履约无关；已成交订单的买家从订单进详情应看到「履约中／已完成」而非「违规下架」，否则会以为订单要黄。

**404 问题**：不 404，返回 200 + 骨架（名称、图、卖家、状态标签、可公开原因），购买按钮置灰并给原因；仅 id 不存在才 404。理由：订单／举报／通知都以详情页为落点，404 会让历史订单链接死掉；断网演示时分不清「不存在」与「不可见」；下架语义是「存在但不可交易」。

**原因枚举**（固定 code，走 200 业务码、文案分离）：NOT_FOUND、PENDING_REVIEW、REJECTED、OFF_SHELF、VIOLATION、SOLD、LOCKED（带 remainingSeconds、orderId）、SELF_ITEM、DUPLICATE_ORDER。必须分开：① 下一步动作不同（等倒计时／找卖家／换搜索／无解）；② 可恢复性不同，M02 靠 code 决定重试还是直接拒；③ 驳回理由只给卖家，统一文案会泄内容；④ 一个 code 一条用例，合并成「不可购买」即不可验收；⑤ 多因并存定优先级（锁定 ＞ 违规 ＞ 售出）。

## T-Z08　AI（需求工程师）

结论：不引独立检索服务，本地 LIKE 直查。

- **部署成本**：单文件 SQLite、断网可演示；加 ES／Meilisearch 多进程、多端口、多内存、多启动脚本，四人课余维护不起，换台机器可能起不来。
- **索引同步**：写路径散在 M04／M06（发布／改版／审核／上下架／处置），双写要处理重试与最终一致，故障表现为「搜不到」或「搜到已下架」，最难查。
- **故障面**：LIKE 的故障面等于数据库本身；多一个服务就多一个演示单点。

会失去：相关度排序、中文分词、拼写／拼音纠错、多字段灵活组合；大结果集分页线性退化；多词要多次 LIKE。1000 条 10 并发下不构成性能问题，损失的是「聪明度」。

必须重估：商品过 5 万或列表 P95 ＞ 200ms；需要相关度／分词；频繁 database is locked；跨字段组合查询索引覆盖不了。课程规模到不了。

（同轮补充：租约的归属要定清楚——锁表归 M02、目录只读；两人同抢要用一条带条件的 UPDATE 定胜负，不能先查后写；租约到期与 2 分钟付款期必须同源同时刻，否则会出现「锁放了订单还活着」。举报记录要存举报时刻的 versionId；处置 v1 不连带 v2 留了后门，审核页应展示该商品历史处置。）

## T-Z09　AI（项目经理）

判断：**有条件做**——不放在 M06 里顺手发，由 M08 排期实现。

1）成本：M06 只加「处置完成」领域事件和必要字段（半天）；发送、模板、幂等与失败重试复用 M08 通知管道（约一人日）。M06 自己发等于重造通知链路，两天起步。

2）收益：卖家不知道下架原因，举报工单会回流成客服问题，M07 售后被动；自动通知一次讲清原因与申诉入口，减少重复答疑和误判投诉。

3）风险：误发、重复发、泄露举报人身份。通知正文不得含举报人信息；只在「待处置→已处置」状态跃迁时触发一次，保证幂等。

排期：M06 的处置状态机与审核记录验收通过后接入；M06 只发事件（或写 outbox 表），M08 订阅消费并投递。依赖单向 M06→M08，通知不得反查审核表。

另外，「页面要快」最容易漏掉的指标：处置完成到卖家可见通知的 P95 送达时延。
