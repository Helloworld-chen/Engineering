# 第四章 实践综述

## 4.1 实践工作综述

本次大作业以校园二手商品交易系统为统一载体，团队 4 人，本人负责 M07（售后审核与客服裁决）与 M08（通知与业务时钟）两个模块。三个专项任务在同一项目上依次推进：需求分析形成需求基线，架构设计在基线上完成方案评审与精化，需求变更追溯基于已完成的代码与测试开展影响分析。

需求分析专项：完成阶段 1.0 自主初析、阶段 2.0 与虚拟同伴的五轮协作修订，以及阶段 3.0 工程化审定，形成 S01～S19 功能条目、可量化的质量要求、开发约束与两个核心用例；通过前后对比表记录了初稿到定稿的主要修订。

架构设计专项：完成上下文整理、评审员 A/B 两套草案、书记员分歧点汇总与合并折中裁决，并对售后与通知模块进行精化，形成架构图、售后单状态机、内部接口与数据表设计，新增任务代次、通知去重键和请求幂等三项关键细节。

编码与测试：在团队骨架（Java 21 + Spring Boot + MySQL + Vue，Docker Compose 部署）上实现 M07、M08 的正式提供者，包括售后单状态流转与裁决、业务时钟、到期任务恢复与分发、站内通知与 SSE 提示。代码通过配置开关与演示实现互斥，可逐模块替换。

测试过程记录了一个真实问题：首次验证时，卖家通知列表查询结果为 0，约两秒后再次查询变为 6 条。起初怀疑通知未生成，排查后确认通知由 outbox 异步分发（约 500 毫秒扫描一次），测试在业务响应后立即断言，早于分发完成。修改方式是在测试中轮询等待通知生成，而不是立即断言；该问题也说明通知投递与业务事务是分离的，业务提交成功不代表通知已送达。

## 4.2 课程与实践反思

开发前，我对需求分析的理解停留在“把功能列出来”。经过三个专项，我认识到需求的价值在于可验证：同一条“超时转客服”，如果不写清期限起算点、责任归属和升级出口，开发与测试都无法判断对错。把质量要求量化成“在什么条件下、什么指标、达到什么阈值、用什么方法验证”，是这次最大的方法收获。

架构方面，我原以为功能定完就该直接写代码。评审员 A 与 B 的对照让我看到，同一个模块可以用完全不同的方式组织：事件驱动更易扩展，同步分层更易交付，两者没有唯一答案，取决于工期、团队规模和变化预期。最终选择合并折中，是在 8 天工期约束下主动放弃部分可修改性，而不是追求“最先进”的方案。

与 AI 协作让我体会到它的边界：AI 能快速给出结构完整的需求列表和架构方案，但会默认引入现实中不存在的复杂度，也会把“看起来合理”的规则当成事实。真正需要人做的是取舍——哪些必须做、哪些本期不做、哪些风险不能接受。每次采纳前追问“为什么”和“如果失败会怎样”，比直接复制输出更有价值。

职业素养方面，这次实践让我更重视留痕与可追溯：需求编号、决策记录、对话日志、测试结果都要能对应到具体来源。代码与文档同步维护虽然费时，但正是这些记录让后续变更、评审和交接成为可能。
