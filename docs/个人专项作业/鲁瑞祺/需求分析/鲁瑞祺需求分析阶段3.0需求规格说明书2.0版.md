## 一 文档目的与依据

本文规定本人负责的用户身份与权限、商品发布与维护两个模块的功能、业务规则、质量要求及验收标准，作为架构设计、编码、联调和测试的依据。

本文基于2026年11月5日的个人需求初稿、阶段2.0实际协作记录及阶段3.0审定决定，由AI辅助整理。本人已确认账号规则，并对图片、商品维护、改价审核、库存变化及验收标准五项建议回复“都接受”。采纳的AI建议在对应条目后标记【VP-Adopted】。

本版本是个人模块的需求基线，不代表组员已确认全部跨模块细节。订单取消条件、超时长度、资金和退货流程由交易、售后负责人确定，双方在相关功能编码前核对接口约定。本文中的验收标准是测试目标，尚不是已通过的测试结果。

## 二 用户与项目边界

### 2.1 使用者

| 使用者 | 主要目标 | 权限边界 |
| --- | --- | --- |
| 未登录访问者 | 注册、登录及访问允许公开的数据 | 不得维护资料、发布商品或操作受限数据 |
| 普通用户 | 维护本人资料，作为卖家发布和维护商品，通过交易模块购买商品 | 同一账号可作为买家和卖家，不得操作他人受限数据 |
| 管理员 | 通过管理及审核模块执行授权操作 | 普通用户不得自行取得管理员权限 |
| 客服 | 通过售后模块执行授权操作 | 客服权限与管理员权限分别检查，不合并授权 |

### 2.2 个人职责与协作

- M03负责注册、登录、退出、本人资料、密码保护及统一身份权限校验。
- M04负责商品内容、图片关联、发布、修改、下架，以及审核和交易引起的商品状态及数量更新。
- 陈玉豪负责统一前端及交易主线，前端调用本人接口，交易服务发起库存占用、售出和释放操作。
- 刘志成负责公开查询、审核等模块，产生审核决定；M04校验决定所针对的商品版本，再更新商品。
- 索圆朋负责的客服和通知相关功能复用身份权限检查；会话失效后，推送连接不得继续访问受限内容。

### 2.3 边界与非目标

系统在本地运行，支付、资金流转和物流使用模拟数据，不接入真实支付、快递或学校统一身份认证服务。暂不收集学号和手机号，因此不能保证注册者一定是本校学生。【VP-Adopted】

本期不提供商品发布后的手动补货或库存调整功能；库存只随合法交易操作变化。【VP-Adopted】账号找回、短信验证、真实支付和真实物流不纳入本人本期功能范围。

## 三 功能需求

沿用个人需求编号L01～L09。后续架构、实现文件和测试用例继续使用这些编号追溯；团队FR、NFR编号在团队总稿核对后补充，不在本次重新编造对应关系。

### L01 用户注册

1. 必填字段为登录名、密码、确认密码。确认密码只用于一致性校验，不持久保存。【VP-Adopted】
2. 登录名长度4～20位，仅允许英文字母、数字和下划线，不区分大小写；`User01`和`user01`视为同名。【VP-Adopted】
3. 密码长度8～64个字符，密码和确认密码必须一致。【VP-Adopted】
4. 注册创建普通账号，不能由注册请求指定管理员或客服身份。登录名唯一；失败不能留下部分账号记录。

验收：合法信息创建一个普通账号；必填缺失、格式错误、密码不一致或同名时拒绝并说明原因。同名并发注册只能成功一次。

### L02 登录与退出

1. 正确凭证建立有效会话，错误凭证不建立有效会话。受限操作从会话取得用户身份，不以请求中的操作者用户号作为身份依据。
2. 会话从登录成功起固定2小时有效，不随访问续期；满2小时后重新登录。退出立即使当前会话失效。【VP-Adopted】
3. 会话失效后，受限查询、修改和推送访问应被拒绝。

验收：正确登录成功，错误账号或密码不能登录；未到期会话可访问受限接口，到期及退出后的旧会话均被拒绝。可使用受控业务时间验证到期边界，不必实际等待2小时。

### L03 本人资料维护

普通资料维护现阶段只允许修改昵称，长度1～20个字符；昵称在注册后填写。不能通过此接口修改登录名、角色、余额或他人资料。【VP-Adopted】

验收：合法昵称保存后查询显示新值；非法长度、越权字段和他人目标操作不能生效，失败后原资料不变。

### L04 身份与对象权限

后端按当前身份、角色、操作类型及数据归属检查权限。商品归属以商品记录和当前会话判断，不能通过替换用户号、商品号等参数绕过检查。订单、私有凭证等跨模块数据，由对应模块调用权限能力并补充对象归属检查。

验收：用户A不能修改用户B的资料或商品；普通用户不能执行管理员操作；客服不能仅凭客服角色执行管理员专属操作；越权失败不改变原数据。

### L05 密码保护

密码以带盐单向散列保存，不保存明文。明文密码和确认密码仅供必要的输入与验证，不在响应中回显，也不得写入业务日志；密码散列不得出现在页面、接口响应和业务日志中。算法及参数在架构设计阶段确定。

验收：检查账号存储、响应和日志，确认没有上述泄露；正确密码验证通过，错误密码验证失败。

### L06 商品发布与图片

1. 已登录卖家填写名称、描述、图片、单价和库存数量；系统从会话记录卖家身份，不接受冒用他人的卖家号。
2. 一条商品记录允许对应多件同款商品，买家每笔订单可以选择购买数量。【VP-Adopted】
3. 发布库存和购买数量必须为正整数；单价必须大于零，最多两位小数。【VP-Adopted】
4. 图片限JPEG（含JPG）、PNG，1～5张，每张不超过5 MiB（5,242,880字节）。后端按实际内容校验，不仅检查扩展名。【VP-Adopted】
5. 图片与上传者、商品关联，不允许引用他人的私有图片。校验或上传失败不能留下有效的错误商品图片引用。
6. 新商品保存为待审核状态，在审核通过前不进入公开商品列表，不接受新购买申请。

验收：合法发布返回商品编号，字段及卖家归属正确；未登录、缺少必要信息、非法单价、非正整数数量、图片越界或校验失败时拒绝，失败不创建部分商品记录。

### L07 商品修改与成交信息保护

1. 只能修改本人商品。保存前检查最新商品版本；旧版本保存失败并提示刷新，不能覆盖新记录。
2. 只要存在有效订单占用，即禁止卖家修改商品内容、价格或下架。没有占用且仍有未售数量时允许维护；全部售出后卖家只可查看，不能直接修改。【VP-Adopted】
3. 发布后不提供卖家手动补货或库存调整，无论是否存在占用均不能直接修改库存。【VP-Adopted】
4. 名称、描述、图片或单价修改后重新进入待审核状态，从公开列表隐藏并停止新购买申请；通过后按当前出售条件恢复展示。【VP-Adopted】
5. 已有订单保存原成交单价、数量及金额，不因后续商品修改、重新审核或下架而改变。部分售出的商品在允许维护时，也不能改写已售订单资料。

验收：修改他人商品、旧版本保存、占用期间修改、手动改库存、全部售出后修改均被拒绝；允许的内容或改价操作成功后触发重审与隐藏；原订单成交信息不变。

### L08 商品下架

卖家可以下架本人未全部售出且无有效订单占用的商品。下架后公开查询不再列出，也不允许新购买申请；已有订单及历史资料保留。有有效订单占用时拒绝卖家下架。【VP-Adopted】

管理员因违规进行的管理下架由审核／管理模块决定，不与卖家下架权限混同，不得删除或改写订单历史。是否影响订单继续履行由对应交易／售后规则决定。

验收：合法下架后公开列表不再列出，历史订单仍可由有权限者查询；越权或占用期间下架失败，原商品和占用不变。

### L09 审核与交易状态协作

1. 审核状态至少区分待审核、通过、驳回。审核更新校验调用权限及商品版本，旧审核结果不能覆盖新内容。卖家可以查看审核结果及驳回理由，并在满足维护条件时修改重提。
2. 提交购买申请时不占用库存；卖家接受时复查身份、商品审核、上下架状态和数量，条件满足才占用对应数量。【VP-Adopted】
3. 只有审核通过、未下架且可购买数量足够，才能接受新交易；不能因仅仅审核通过就绕过库存或下架判断。
4. 可购买数量不足时，整份接受失败，不自动减少数量、不部分成交，不留下部分订单或占用更新。【VP-Adopted】
5. 同一订单只能占用一次；交易模块确认合法取消或失效后，对应占用只释放一次；完成出售时将占用转为已售，不能再次扣减可购买数量。【VP-Adopted】
6. 重复接受、释放和售出请求不能再次改变数量。不存在有效占用或状态不允许时，不能把已售数量当作可释放占用。退款、退货不等同于取消未完成订单，不能直接套用占用释放操作。
7. 只占用部分数量时，剩余数量仍可供其他申请使用；售罄与部分售出需通过数量区分，不能用一个整条商品的“已售”标记代替数量判断。

验收：无权限、版本过期、审核未通过、下架或库存不足时拒绝。并发接受不能超卖，重复操作只能产生一次数量变化，业务记录与数量结果一致。

## 四 业务数据与状态约定

### 4.1 业务信息

| 对象 | 必须保留的信息 | 用途 |
| --- | --- | --- |
| 账号 | 用户编号、唯一登录名、密码散列、角色、昵称 | 身份与资料维护 |
| 会话 | 会话标识、用户编号、登录和到期时间、有效状态 | 校验固定有效期及退出 |
| 商品 | 商品编号、卖家编号、名称、描述、单价、图片引用、审核与上下架状态、版本、初始总量及库存相关数量 | 内容维护、审核、出售判断 |
| 图片 | 图片标识、上传者、实际类型、存储引用、商品关联 | 文件校验与归属检查 |
| 订单关联 | 订单编号、商品编号、购买数量、原成交信息、对应占用及处理状态 | 由交易模块管理，支持一次性数量变更和历史查询 |

本表规定业务信息，不固定数据库表结构。不得通过普通资料接口修改角色、余额，也不得由前端直接指定库存处理结果。

### 4.2 数量关系

本期商品发布后不手动补货或调库存，正常交易中应始终满足：

> 可购买数量＝发布时库存总量－有效订单占用数量－已售数量。

各项数量不得为负，有效占用数量与已售数量不能重复计算。接受申请增加占用；合法取消或失效减少对应占用；完成出售减少对应占用并增加同等已售数量，因此售出转换不会再次减少可购买数量。【VP-Adopted】

退货后的库存归属和重新销售由交易、售后模块另行约定，不能擅自修改已售数量。本版不提供卖家手动调整，也不把退款或退货直接当成释放库存。

## 五 验收用例

以下为已审定的检查目标，全部尚未执行。正确性检查同时核对接口结果、商品数量和订单记录，不能仅凭页面提示成功判断。并发场景使用合法、互不重复的申请；涉及取消、售出的场景以交易模块允许该动作的状态为前置条件。【VP-Adopted】

| 编号 | 对应需求 | 输入或操作 | 预期结果 |
| --- | --- | --- | --- |
| TC-01 | L01 | 合法注册后，再注册大小写不同的同名账号；另测同名并发注册 | 只创建一个普通账号，重复注册失败 |
| TC-02 | L01 | 登录名长度3、4、20、21；非法字符；密码长度7、8、64、65；两次输入不一致 | 合法边界通过，非法值拒绝且无部分账号记录 |
| TC-03 | L02 | 正确凭证、错误凭证、退出后重用原会话 | 仅正确凭证能登录，旧会话不能访问受限数据 |
| TC-04 | L02 | 登录未满2小时及满2小时分别访问，期间持续发出请求 | 未满时有效，满2小时失效，访问不续期 |
| TC-05 | L03、L04 | 昵称长度0、1、20、21；修改角色、余额或他人资料 | 合法昵称可保存，非法值及越权字段不生效 |
| TC-06 | L04、L05 | 两个普通账号交叉访问受限对象；检查存储、响应和业务日志 | 越权被拒绝；不保存明文密码，不泄露密码及散列 |
| TC-07 | L06 | 合法发布；图片0、1、5、6张；单张刚好5 MiB及超限；伪装扩展名 | 合法值通过；超限、数量非法和实际类型不符被拒绝 |
| TC-08 | L06 | 单价0、负数、两位及超过两位小数；数量0、负数、小数和正整数 | 只接受正数且至多两位小数的单价、正整数数量 |
| TC-09 | L07、L09 | 商品版本变化后，再提交旧版本修改或审核结果 | 拒绝覆盖，当前内容与版本不被旧请求改变 |
| TC-10 | L07 | 无占用且未售罄时修改名称、描述、图片或单价 | 修改成功后待审核并隐藏，通过后按出售条件恢复 |
| TC-11 | L07、L08 | 存在占用时修改或下架；尝试手动调库存；售罄后修改 | 全部拒绝，原业务数据与占用不变 |
| TC-12 | L08 | 无占用且未售罄时合法下架，再查公开列表和历史订单 | 公开列表不再列出，已有订单仍可查询 |
| TC-13 | L07 | 形成订单后，在后续满足维护条件时合法修改商品 | 已有订单保存的单价、数量和金额不变 |
| TC-14 | L09 | 剩余1件，接受购买2件的申请 | 整份失败，不自动改为1件，不留下部分占用 |
| TC-15 | L09 | 初始3件，两份各买2件的申请并发接受 | 恰好一份成功，另一份库存不足；占用2件，可购买1件 |
| TC-16 | L09 | 初始1件，10份各买1件的申请并发接受 | 恰好一份成功，其余失败，数量不为负 |
| TC-17 | L09 | 重复接受同一申请；重复释放同一订单；重复确认售出 | 每项操作最多产生一次对应数量变化，不重复占用、释放或售出 |
| TC-18 | L09 | 初始3件，接受2件；合法取消后释放；再接受另一份2件申请 | 取消后可购买量恢复为3；再次接受后占用2、可购买1 |
| TC-19 | L09 | 初始3件，接受2件并完成出售 | 已售2、占用0、可购买1；不发生二次扣减 |
| TC-20 | N-L04 | 保存账号、商品、审核、库存及图片引用后正常重启 | 重启后查询结果一致，图片仍可访问 |
| TC-21 | L06、L09 | 待审核、驳回或下架商品提交新购买申请／接受操作 | 不能绕过不可购买状态；被拒绝操作不产生占用 |

并发检查在每轮恢复相同初始数据后执行，记录成功数、失败原因及最终数量。测试工具、接口路径和精确并发调度方式在实现阶段确定。

| N-L05 | 失败提示 | 重复登录名、会话失效、无权限、字段错误、版本冲突、库存不足可区分；每种拒绝均核对无部分业务更新 | 沿用既有个人需求 |
| N-L06 | 本地性能 | 在同一演示电脑、100个账号、1000条商品、500笔订单下，10个并发会话持续1分钟；成功读取请求P95≤2秒，成功修改请求P95≤3秒 | 本轮采纳【VP-Adopted】 |

性能测试记录设备配置、应用及数据库版本、接口范围、请求数量、错误数和延迟分位数。读取与修改分别统计，不能混合统计，也不能用快速失败请求代替成功请求达标。测试数据和操作应满足权限及状态前置条件；正确性失败不能用响应快解释为通过。

接口选择、测试工具和设备明细在测试执行前登记。当前不填写实测延迟、通过率或“测试通过”。

1. 四人统一语言、框架、关系数据库和接口约定，前后端及文件在本地运行或保存。技术选型在架构阶段确定。

3. 前端需统一注册字段、会话方式、商品数量、错误提示和版本冲突刷新流程。
4. 交易模块需统一申请与订单的区分、成交信息保存时点、接受／取消／失效／完成的状态依据、请求识别方式及数量转换。相关组合操作应整体成功或整体失败。
5. 审核模块需统一商品版本、改价重审、审核期间隐藏以及管理下架调用。
6. 通知模块需统一会话失效及状态变化提示，不能以通知到达代替读取最新业务结果。

交易取消条件、超时长度、退款和退货流程属于跨成员规则，需由负责人共同核对。本人确认的是商品模块接受合法业务依据后的处理要求，不代表已经替其他成员审定其规则。核对如引起本需求变化，保存修订和影响记录后再实施。
