# 阶段2 方案评审与裁决

本阶段按专项任务书要求，由虚拟评审员 A（可修改性视角）与评审员 B（可交付性视角）分别给出两套模块实现草案，书记员汇总分歧点，本人作出裁决。评审对象为阶段1 整理的 M07（售后审核与客服裁决）与 M08（通知与业务时钟）；两套草案均位于团队总稿“分层单体 + 局部事件”的框架内，差异集中在模块协作方式、通知与期限的实现。

## 2.1 方案A：事件驱动协作与接口隔离

架构风格：事件驱动协作（EDA）与端口—适配器隔离，运行形态仍为单个后端应用。售后模块在业务事务内保存领域事件，由独立分发器投递；资金、时钟与通知通过接口注入。

取舍依据：把资金接口、通知渠道与演示时间三处易变点隔离在接口之后；新增通知方式只需增加订阅者，不改业务代码。代价是事件契约、失败重试与重复处理逻辑增加。

**表2-1 方案A的组件与职责**

| 组件 | 职责 | 关键依赖/通信方式 | 隔离的易变点 |
| --- | --- | --- | --- |
| AfterSaleService | 售后单状态机、决定记录与业务校验 | 同库事务；经 FundPort 调 M02 资金；发布领域事件 | V-S2 售后期限规则 |
| OutboxEventStore | 保存待投递事件 | 与业务修改同事务写入 | V-S3 通知渠道 |
| EventDispatcher | 轮询事件表并投递给处理器，失败重试 | 调用 NotificationHandler、PushHandler | V-S3 通知渠道 |
| NotificationHandler / PushHandler | 生成站内通知、产生页面提示 | 读取事件载荷；写通知表 | 收件人规则 |
| ClockAdapter / DeadlineAdapter | 提供统一业务时间与期限 | 实现 ClockPort、DeadlinePort | V-S4 演示时间推进 |
| FundPortAdapter | 封装 M02 资金接口 | 适配器内同步调用，事务内生效 | V-S1 资金接口契约 |

## 2.2 方案B：分层同步调用与最小事件

架构风格：分层单体（Web 交互层、业务层、数据访问层）与同步调用，不引入独立事件通道。通知在业务事务提交后由通知服务写入通知表，页面轮询获取未读数；期限由截止时刻表加定时扫描实现。

取舍依据：组件少、事务边界单一，四人小组容易理解与联调；页面轮询避免推送连接的调试成本。代价是新增通知渠道需要修改业务完成后的调用代码，通知失败的重试要写在服务内部。

**表2-2 方案B的组件与职责**

| 组件 | 职责 | 关键依赖/通信方式 | 隔离的易变点 |
| --- | --- | --- | --- |
| AfterSaleService | 售后单状态机、决定记录与业务校验 | 直接同步调用 TradeService、FundService，共享同一事务 | V-S1 资金接口契约 |
| DeadlineScheduler | 扫描到期任务并调用业务方法 | 读取 Deadline 表；调用 AfterSaleService | V-S2 期限规则 |
| NotificationService | 写入站内通知与未读状态 | 业务提交后调用；页面轮询查询 | V-S3 通知渠道 |
| ClockService | 提供统一业务时间 | 单例服务，供各业务调用 | V-S4 演示时间推进 |

## 2.3 两种方案的主要分歧

书记员仅汇总分歧、不评价优劣。分歧点归并为以下四条：

**表2-3 分歧点清单**

| 序号 | 分歧点 | 方案A | 方案B | 分歧原因（设计原则） |
| --- | --- | --- | --- | --- |
| 1 | 模块协作方式 | 业务完成后发布事件，处理器订阅；模块间接口调用少 | 业务服务直接同步调用相邻模块 | 解耦程度与控制流可理解性之间的权衡 |
| 2 | 事务与失败处理 | 业务事务只保证自身与事件落库，通知最终一致 | 业务与通知在同一调用链内完成，失败可立即回滚 | 一致性与可修改性的取舍 |
| 3 | 通知能力扩展 | 增加处理器即可扩展渠道，业务代码不动 | 新增渠道需修改业务完成后的调用代码 | 开闭原则与实现成本 |
| 4 | 工期与调试成本 | 组件与契约较多，问题需沿事件链排查 | 组件少、链路短，联调快 | 可交付性与避免过度设计 |

## 2.4 裁决结果

裁决结论：合并折中。以方案 B 的分层单体与同步业务事务为基底，借用方案 A 的局部事件机制（仅用于通知）与时钟、期限的接口隔离；拒绝方案 A 将业务模块全部事件化，也拒绝方案 B 把通知逻辑直接写在业务服务中。

**表2-4 裁决结果与依据**

| 处理决定 | 具体内容 | 理由（设计原则） |
| --- | --- | --- |
| 以方案B为基底 | B/S 访问、分层单体、同步业务事务、单个后端应用 | 关注点分离清晰；四人小组可理解、可交付，避免过度设计 |
| 借用A的事件表与分发器 | 业务事务内保存待通知事件，提交后由分发器生成通知，失败重试不回滚业务 | 信息隐藏与解耦：通知失败不影响已完成的交易；新增渠道可加处理器 |
| 借用A的时钟与期限接口 | 业务统一调用 Clock 与 Deadline 接口，实现可替换 | 信息隐藏：演示时间与期限策略变化不扩散到业务代码 |
| 拒绝业务模块全部事件化 | 售后、订单、资金之间仍用同步接口调用 | 【Rejected】业务需要强一致，全事件化增加契约与调试成本（避免过度设计） |
| 拒绝通知写在业务服务内 | 通知不直接写在业务服务的提交路径上 | 【Rejected】扩展与失败处理会污染业务代码（关注点分离） |

**表2-5 裁决认定汇总**

| 编号 | 决策内容 | 标记与来源 |
| --- | --- | --- |
| AD-S01 | 分层单体 + 同步业务事务 + 单后端部署 | 【AI-Adopted】方案B |
| AD-S02 | Outbox 事件表 + 分发器，仅用于通知 | 【Revised】合并A的事件机制与B的事务模型 |
| AD-S03 | 统一 Clock 与 Deadline 接口 | 【AI-Adopted】方案A |
| AD-S04 | 业务模块之间全部事件化 | 【Rejected】方案A，理由：契约与调试成本高 |
| AD-S05 | 通知逻辑直接写在业务服务中 | 【Rejected】方案B，理由：污染业务代码 |

阶段3 将依据本裁决精化 M07 与 M08 的模块结构、数据表、内部接口与售后单状态机，并明确在团队方案基础上新增的关键细节（期限任务代次、请求标识幂等、通知去重键）。
