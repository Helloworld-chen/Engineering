### 3.3　最终架构

本报告沿用团队总架构（B/S、分层单体、同步事务、局部事件，详见团队架构总稿），以下只描述本人切片在其中的位置与内部结构。商品目录与审核处置是业务层内两个并列服务，共享同一数据库与事务；通知通过事务内的待发事件在提交后由 M08 分发，不参与业务状态的一致性。

静态结构上，浏览器只与后端通信，后端按「Web 控制器 → 业务服务 → 仓储/网关」三层组织。M05 与 M06 在业务层是两个并列服务：前者负责读取与判定，后者负责写入审核与处置结论；两者的商品写入都经 M04 的受控接口，不直接改写商品表。

### 3.5　事务、并发与加锁顺序

M05 全部路径只读：列表与详情不加锁、不参与任何事务、不写入商品表，因此不会与下单或审核形成二次加锁。本模块只读取当前版本与状态，不做写入，因此不会形成二次加锁。

M06 的写入路径按固定顺序加锁，避免与下单校验交叉死锁：
- 统一顺序：商品记录 → 审核记录（或举报记录）→ 处置记录 → 审计 → 待发事件。
- 审核：锁定商品 → 读取当前版本与出售状态 → 比对请求携带的版本 → 版本不符则整体回滚并要求重读。
- 处置：锁定举报记录 → 锁定商品 → 校验状态允许下架 → 写处置结论 → 经 M04 改写商品状态 → 写审计与事件。
- 幂等：所有写入接口携带请求标识，同一标识重复提交返回首次结果，不重复生成审核或处置记录。

下表为模块间接口的职责约定。HTTP 路径与框架签名在技术选型确定后补充；操作者身份一律从后端会话取得，不由请求参数传入。

**表3-5　内部接口约定**

| 接口 | 输入 → 输出 | 校验与处理 |
|---|---|---|
| Catalog.search / detail | 关键词、分类、页码 / 商品号 → 商品列表或详情、分页信息、商品版本 | 过滤待审核、已驳回、违规下架；已售出仅返回成交状态，不返回购买入口。 |
| Catalog.search / detail | 关键词、分类、页码 → 列表或详情，附带 purchasable 展示字段 | 供 M02 在事务锁内调用；原因码区分待审核、已驳回、已下架、已锁定、已售出。 |

| Report.decide | 举报号、结论、理由 → 处置结果 | 管理员权限；确认违规时经 M04 下架；已有订单保留；不触发资金操作。 |

### 3.7　失败处理

**表3-6　失败场景与处理**

| 场景 | 处理 | 用户可见结果 |
|---|---|---|
| 商品在列表查询后被下架或锁定 | 以下单事务内的校验结果为准，列表状态不参与判定。 | 下单返回具体原因，页面刷新后展示最新状态。 |
| 审核期间卖家修改了商品内容 | 版本栅栏比对失败，整体回滚，不写入审核结论。 | 提示「商品内容已变化，请重新读取后审核」。 |
| 通知发送失败 | 业务结论已提交，事件保留在待发表中由 M08 重试。 | 审核与处置结果正常展示，通知延迟到达。 |
| 举报凭证文件缺失或类型不符 | 受理阶段校验文件类型与大小，不合规则拒绝，不生成举报记录。 | 提示具体字段错误。 |
| 数据库临时冲突（死锁） | 回滚后重试当前事务，达到上限则返回失败。 | 提示稍后重新提交，操作未生效。 |
