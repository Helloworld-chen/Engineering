### 1.1　编号与缩写说明

M 表示团队功能模块，M01 为统一前端，M02 为交易履约与资金结算，M03 为身份与权限，M04 为商品发布与主数据，M05 为本人负责的商品目录与可见性控制，M06 为本人负责的商品审核与举报处理，M07 为售后审核与客服裁决，M08 为通知与业务时钟。

FR 表示团队功能需求，NFR 表示团队质量需求，AR-01 表示后端向有权限的页面推送业务状态变化提示。T 表示团队需求讨论记录编号；UC 表示用例；Z01 至 Z09 为本人个人需求编号，按模块连续编号。

### 1.2　本人负责的模块及工作边界

M05 负责商品的公开查询、检索与分页，商品可购买状态与版本的对外校验，以及可见性与可购买性的判定规则。M06 负责管理员对商品的审核、用户对违规商品的举报及管理员的处置记录。两者都不涉及订单、资金与售后：订单由 M02 创建并持有，资金变动由 M02 的模拟资金部分执行，退款与争议由索圆朋负责的 M07 受理。

### 1.3　主要用户及目标

**表1-3　使用者与权限边界**

| 使用者 | 主要目标 | 权限边界 |
|---|---|---|
| 买家 | 看到真实的在售商品与可购买状态；对违规商品举报并查询结果。 | 仅读取公开商品与本人举报，不得修改商品。 |
| 卖家 | 查看本人商品的审核结论，按理由修改后重提；了解本人商品被举报后的处置结果。 | 仅维护本人商品；不得执行审核或处置。 |
| 管理员 | 审核待发布商品、处置违规举报、维护商品可见性。 | 可改审核与出售状态，不得裁定资金或退款。 |
| 举报人 | 查询本人举报的处理进度与结论。 | 仅查询本人提交的举报及其凭证。 |

### 1.4　核心功能需求初稿

初稿按模块顺序列举，表述尚未统一，验收方式留待阶段 3.0 补齐。
- Z01 商品列表与详情：显示名称、价格、描述、图片和可购买状态；待审核和违规下架的商品不能出现在公开页面上。
- Z02 检索与分页：按关键词和分类查商品，分页显示，查不到要有提示。
- Z03 可购买状态校验：下单时告诉交易模块这件商品能不能买，不能买要说清原因。
- Z04 上架与可见性：审核通过才能上架，驳回、下架、售出分别对应不同状态，状态不能乱跳。
- Z05 分类与检索字段：维护分类和能搜的字段，分类调整不影响已经成交的订单。
- Z06 商品审核：管理员看内容后给通过或驳回，要写理由；卖家能改完再提。
- Z07 违规举报：用户填理由、传图，举报要有记录、能查进度。
- Z08 举报处置：管理员核实后记录结论，违规的下架，但已有订单不能动。
- Z09 权限与追踪：普通用户不能审核；只能查自己的举报；审核处置要留操作人和时间。

### 1.5　质量需求初稿

- 性能：页面打开要快，列表和详情不能卡。
- 一致性：不能出现商品已经卖掉还能下单，或者已经下架还在列表里显示。
- 可见性：待审核和违规商品绝对不能露出来。
- 隐私：举报人的信息不能给别人看，举报的图也不能随便看。
- 可追溯：审核和处置过程要能查得到，出了问题能说明是谁在什么时候改的。

### 1.6　开发约束初稿

- 四人协作，每人至少负责两个功能模块，本人负责 M05 与 M06。
- 前端、后端、数据库和图片都存在本机，不部署到云端。
- 支付、货款暂管、结算、退款和物流全部本地模拟，不接外部服务。
- 语言、框架和数据库由团队统一确定，确定后记录版本。
- 用 Git 与 GitHub 管理文档和代码。

### 1.7　自我反思

初稿阶段我最不确定的是「商品可购买状态由谁判、判在哪一刻」。原本我以为买家提交申请后由卖家决定，那么排队顺序就是本模块的核心问题；后来意识到真正难的是并发：列表展示的状态在用户点击购买的那一刻可能已经失效。如果只在前端或查询时判断，一定出现超卖或误拒，所以本模块必须对外提供一个能在事务内调用的校验入口，并把商品版本一并返回，让下单一侧能够确认自己看到的就是当前内容。

另一个体会是职责边界。审核通过后究竟由谁改写商品状态，是 M06 直接写商品表，还是经 M04 的受控接口写？初稿倾向于前者，省事；但这样商品主数据就有两个写入方，版本控制会失效。阶段的修订把写入统一收归 M04，M06 只保存审核结论，代价是多一次调用，换来的是状态与版本的可追踪。
